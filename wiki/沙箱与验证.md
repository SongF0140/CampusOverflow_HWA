# 沙箱与验证

这里说的 sandbox 不是“让 AI 在隔离环境里执行治理动作”，而是三类互补的验证边界。

## 1. 治理 dry-run：只预演，不执行

Dry-run 复用审批前的目标状态与版本校验，只读统计动作影响：

```text
POST /internal/agent/user/governance-dry-run
{
  "target_type": "question",
  "target_id": 42,
  "action": "delete",
  "expected_version": "<64 位哈希>"
}
```

返回：

- 当前状态与版本；
- 预计影响的问题/回答/评论数量；
- 风险提示；
- 明确标注“仅供参考，不构成执行”。

约束：

- 不建工单、不写审计、不改目标状态；
- 版本不匹配返回 409；
- 真正执行仍在人工确认后由后端事务完成。

## 2. 测试沙箱：真实 MySQL / Postgres

`campus-overflow-ai/deploy/test-sandbox/` 提供本机 compose：

```bash
cd campus-overflow-ai/deploy/test-sandbox
cp .env.example .env
docker compose up -d
```

默认 MySQL `3307`、Postgres `5433`，数据库名 `campus_overflow_test`。

真实 MySQL 并发用例：

```bash
cd campus-overflow-ai/backend
$env:TEST_MYSQL_URL="mysql+pymysql://root:sandbox_root@127.0.0.1:3307/campus_overflow_test?charset=utf8mb4"
uv run pytest tests/test_patrol_scan_concurrency_mysql.py -q
```

未设置 `TEST_MYSQL_URL` 时自动跳过，普通 CI 不依赖 Docker。

## 3. MCP 沙箱：隔离外部工具

`campus-overflow-ai/deploy/mcp-sandbox/` 只监听本机 `127.0.0.1:8790`，并启用：

- 非 root；
- 根文件系统只读；
- `cap_drop: ALL`、`no-new-privileges`；
- CPU/内存/PID 上限；
- 不注入数据库变量；
- 只注册现有只读工具。

生产还需在编排层限制出站网络，并用 secret 文件提供后端服务 token，不能把 token 写进 compose。

## 边界

- dry-run 不能替代审批，也不作为执行凭证；
- 测试沙箱不承载真实数据；
- MCP 沙箱解决“不可信执行环境隔离”，不解决“动作是否应该执行”；
- 多实例限流与调度仍未收敛，归 T-18。
