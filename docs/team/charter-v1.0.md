## 二、团队价值观

1. **坦诚透明**：问题早暴露、早讨论，不隐瞒进度与风险；评审对事不对人。
2. **责任到人**：任务谁认领谁负责到底，从开发、测试到文档收口闭环交付。
3. **质量优先**：宁可慢一步也不合入带缺陷的代码，测试与文档是交付的一部分而非附加项。
4. **协作共担**：脏活累活（测试、数据处理、冲突解决、文档校对）全员轮转补位，不搞单点依赖。
5. **持续改进**：每次迭代结束做回顾，把教训固化为规约或工具检查。

## 三、沟通约定

1. **例会**：每周至少一次线上/线下例会，同步进度、风险与下周计划；紧急事项随时拉短会。
2. **日常沟通**：QQ 群/微信用于日常沟通，重要结论必须落到仓库文档或 issue 中，口头结论不作为唯一依据。
3. **响应时限**：工作日期间消息尽量 24 小时内回复；PR 评审请求 48 小时内给出结论，超时可催办。
4. **任务认领**：任务在 issue/任务表中认领，认领时明确预计完成时间；连续 3 天无进展需主动说明并重新分配。
5. **冲突处理**：技术分歧先查 `docs/` 与 `specs/` 依据，仍有争议由 Scrum Master 组织讨论定案并记录决策；非技术分歧少数服从多数，重大分歧提交课程教师协调。
6. **会议记录**：例会结论、变更决策写入 `docs/`，保证可追溯。

## 四、开发规约

1. **规格驱动**：需求（WHAT）写 `specs/`，实现方案写 `plan`/`docs/`；修改规格后进入开发前必须重跑一致性分析。
2. **分支管理**：`main` 保持可运行；从 `main` 拉特性分支 `feat/<简述>`，修复用 `fix/<简述>`，文档用 `docs/<简述>`；禁止直接向 `main` 推送未评审代码。
3. **提交规范**：commit message 使用 `<type>: <简短中文描述>`（feat / fix / docs / test / chore / refactor / style），小步提交、不攒大 diff。
4. **代码评审**：所有变更经 PR 合入，至少一名成员评审通过；评审关注正确性、可读性、测试与文档，冲突问题当面说清。
5. **质量门禁**：后端 `ruff check`、前端/Agent `eslint` 零 error；`pytest` / `vitest` 相关测试通过；涉及表结构变更跑 `alembic upgrade head`。
6. **测试要求**：核心流程必须有测试；开发期冒烟按改动范围跑，批次收口前 CI 全量回归绿。
7. **文档同步**：接口、架构、流程变更必须同步对应文档；审查记录写入 `docs/审查记录/`（设计依据、验证记录、决策说明三节）。
8. **安全红线**：不提交密钥、token、数据库密码；Agent 不得绕过 FastAPI 直连数据库；高风险操作必须人工确认并留审计。
9. **命名与风格**：Python 蛇形、TypeScript 小驼峰，接口字段一律蛇形；用户可见文案用简体中文；函数不超过 80 行；禁止空 catch。

## 五、DoD 初版（Definition of Done）

一个任务满足以下全部条件才算"完成"：

- [ ] 需求与验收标准明确，任务已在任务表/issue 中登记并关联需求编号；
- [ ] 代码完成并通过本地 lint（ruff / eslint 零 error）；
- [ ] 核心流程测试（单元/接口）已补充，相关测试全部通过；
- [ ] 涉及数据结构变更的，迁移脚本可重复执行且已验证；
- [ ] 相关文档（接口、架构、流程、审查记录）已同步更新；
- [ ] PR 已由至少一名成员评审通过并合入 `main`；
- [ ] CI 全量回归通过，无新增告警；
- [ ] 简体中文文案正确，无遗留 TODO、调试代码与敏感信息；
- [ ] 验收演示通过（例会/评审中演示或录屏留档）。
