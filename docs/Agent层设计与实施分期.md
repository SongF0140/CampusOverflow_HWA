## 目标架构

保持 Next.js、FastAPI、Agent 三服务分离，沿用 TypeScript、Hono、Vercel AI SDK、Zod，不在本批更换技术栈。

用户请求经 BFF 进入 Agent。FastAPI 校验真实登录态并提供用户身份与课程访问上下文。Agent 在可信上下文内生成计划，经工具注册表和确定性权限策略执行，再总结、自检和记录结果。业务数据查询、工单、Wiki 草稿与发布均经 FastAPI 白名单接口完成；MySQL 由后端统一管理。个人记忆按最新决定保存在浏览器，不作为用户身份或数据权限依据。

外部内容、模型输出和客户端传入的角色、用户 ID 均不能授予权限。外部 Agent 接入、MCP 工具也不能绕过内部策略。高风险处置保持管理员确认、后端执行的边界。

## 首批：可信身份与受控运行主干（已确认方案）

### 范围和交付结果

首批交付从用户请求到运行结果的受控链路：身份校验、计划生成、工具权限检查、执行、总结自检与后端运行记录。以现有课程和问题检索工具验证主干，暂不在同一批引入 Wiki、后台调度或真实 MCP。

保留现有四类任务及其结果结构，修正默认检索客户端未传入任务上下文的问题。结构化推荐继续保留真实候选过滤与真实标签 ID 映射。已有聊天流式协议在兼容范围内复用；本批不新增面向用户的完整 AI 页面。

### 身份和授权

- BFF 从现有 HttpOnly 登录 Cookie 提取凭证并向 Agent 转发；Agent 经新增后端内部身份解析能力获取可信 principal，不共享 JWT 签名密钥。
- 内部身份解析同时要求有效服务凭证和用户登录凭证；无效、过期、封禁身份直接拒绝，不降级为匿名或管理员。
- 工具依赖从运行上下文取得用户身份，禁止接受模型生成的操作者角色和用户 ID 作为授权依据。
- 计划生成前只提供获准工具；执行前再次检查。数据范围由 FastAPI 复核，不只在 Agent 侧过滤。
- 本批接口不能把原有服务级检索直接暴露为任意用户的全站特权查询。查询范围遵守现有已登录读取、课程可见性和治理隐藏规则。

### PlanList 和执行

- 计划由结构化步骤组成，步骤至少包含唯一 ID、目标说明、工具名称与参数，整体经 Zod 校验。
- 首批采用顺序执行，每次执行都在固定工具白名单内。首轮计划最多 8 步；执行总预算最多 12 次工具调用，返工不得重置预算。
- 工具调用结果是后续步骤和总结的依据。后续参数需要使用前序结果时，由程序在当前上下文中解析和校验，不能执行字符串模板代码或任意表达式。
- 总结先做结构校验与确定性来源检查，再进行模型自检；自检不能提升权限或放宽来源检查。最多返工 1 次，仍未通过则失败，不返回未通过校验的最终建议。
- 工具名称未知、参数不合法或权限不足时拒绝该调用；权限错误不自动重试。首批只有只读工具，其他工具在各自批次接入审批与幂等策略后才能开放。
- 单次上游请求默认 60 秒超时，整次运行默认 180 秒；超时通过 AbortSignal 传播。取消、失败均写运行终态，取消和超时不被误记为成功。
- 首批不提供进程重启后自动恢复执行。持久化计划仅供追踪，不能把已有成功步骤自动重放。

### 记录和故障处理

- 使用统一的 agent_run_id 和 trace_id 关联运行、计划摘要、步骤、工具调用与结果摘要，HTTP 字段采用蛇形。
- 替换内存记录器，通过已有后端 runs/tool-calls 接口写入；若计划和步骤追踪需要新增字段或表，由 Alembic 增量迁移实现。
- 日志只记录受控、脱敏摘要，不存密码、凭证、原始思维过程或完整隐私原文。允许保存简短计划说明，不要求模型输出内部推理。
- 创建运行记录失败时，不进入模型或工具执行；执行过程中审计持久化失败时停止后续动作并报告失败，不能假报审计成功。
- 运行终态写入失败可能留下 running 记录，必须保留同一运行 ID 的错误日志并让调用方明确获知异常；后续运维收敛能力单列，不声称本批已解决所有崩溃恢复。

## 夜间静默治理（离线整理）

日期：2026-11-17。状态：用户已确认并入本设计并按分期实施；本节只定义方向与分期，参数和存储选型在对应批次开始前定案。

### 与现有静默巡检的区别

现有静默巡检（T-15 B 批）是**在线扫描**：调度器默认 15 分钟一轮，全站三类内容 union，逐条 LLM 评估，60 秒限时，中高险建单，低风险仅审计，单条失败隔离，幂等 repeat，工单 source=agent。

夜间静默治理是**离线整理**，不重扫全站。两者分工固定：

```text
在线（每 15 分钟）：只对新内容初筛，保持现有建单规则与限时
离线（夜间）：纠错、聚合、提炼规则、发现缺口
```

夜间任务不新增处置能力，不修改已发出工单，只产出"下一轮巡检可用的参考"和"待人工确认的线索"。

### 四层结构

沿用 Anthropic Components of Agent Memory 的分层思路，映射到治理场景：

| 层 | 内容 | 要求 |
| --- | --- | --- |
| 巡检原始记录 | 内容快照、模型版本、判定、理由、耗时 | 完整、只追加、作为核对依据 |
| 巡检笔记 | 反复误判、规则边界、漏报线索 | 数量受限，每条带来源 |
| 治理表征 | 按内容类型与风险类型整理的边界案例与规则 | 与原始记录检索结合，不单独使用 |
| 注入上下文 | 下一轮巡检预加载的规则集 | 硬性 token 上限，可撤回 |

原则：笔记必须小。参考量级来自公开实验：记忆文件从数百个降到十余个反而效果更好；结构化组织与检索结合优于任一单独使用。

### 任务一：判定反馈闭环（优先）

- 读取最近 N 天的"巡检判定"与"管理员最终处置"（accepted / rejected / skip / warn），生成三类结果：
  - 误报模式：模型建单但管理员 skip 或驳回；
  - 漏报线索：管理员手动处置但无对应巡检单；
  - 规则失效：某规则近期驳回率异常升高。
- 输出只作为下一轮巡检的参考规则与优先级建议，不改历史工单、不自动调参生效。
- 反馈数据不足时不生成结论，明确记录"样本不足"。

### 任务二：巡检笔记与预算

- 每轮最多产出固定条数笔记，按"是否影响未来判定"筛选；一次性事件与无复用价值内容不写入。
- 每条笔记必须包含：来源工单或内容标识、内容类型、规则版本、模型版本、有效期、置信度、脱敏摘要。
- 不保存隐私原文、凭证或完整用户内容，遵守 C-07。
- 过期笔记降级为"参考"，不得单独作为建单依据。

### 任务三：规则提炼与注入

- 只有连续多次判定与管理员处置一致的模式，才允许提升为预加载规则。
- 注入上下文设 token 上限；超出时只保留规则与指向案例的引用，不塞全文。
- 规则带版本号，可撤回；撤回后立即从注入上下文移除。
- 安全类硬规则仍由确定性策略执行，不由模型自由改写。

### 任务四：目标发现与缺口检测

- 输出"下阶段关注点"建议，例如某课程某类问题集中、某规则申诉率异常、某作者反复触发同类风险。
- 输出"缺口清单"，例如有单长期无人处置、有申诉找不到规则、管理员手动处置但巡检从未建单。
- 两类输出都只交人工确认，不自动扩大扫描范围、权限或处置能力。

### 边界

1. 夜间不自动处置。AI 只建单或产出建议，人工确认后由 FastAPI 执行（C-06 不变）。
2. 巡检笔记属于系统级治理审计，不是个人记忆，不与个人记忆表混用（C-07）。
3. 夜间任务失败不影响在线巡检；失败记录必须可追踪，不静默跳过。
4. 默认关闭或受开关控制，未配置时明确不可用。

### 验证指标

- 误报率、漏报率、建单准确率；
- 管理员驳回率（最直接）；
- 同类误判重复次数（验证纠错是否阻止传播）；
- 每轮 token 成本、夜间任务耗时、失败率。

指标必须在同一批已标注历史内容上对比改造前后，未采集数据前不报告收益。
