状态：已实现 AP-01 只读现状、AP-02A 治理预览与 AP-02B 持久申请；AP-03 执行检查点、挂起/恢复尚未实现，不能将当前模块称为完整审批协调。

## 2026-10-28 AP-02B 实施结果

- 预览增加目标版本；提交时必须携带相同版本、UUID 申请标识和明确的动作/参数。
- 双凭证与数据库管理员权限校验后，后端锁定目标核对版本；申请 run、pending 工单与管理员通知同事务保存，无新表或迁移。
- 相同管理员以相同标识和参数重试返回原工单；改动作/原因/期限/版本或换管理员复用标识均拒绝。
- 冻结快照约束现有决策入口；目标正文/状态、动作或期限变化时拒绝旧确认。拒绝工单仍可使用 skip；旧格式工单沿用既有状态机。
- 工单已执行后重复提交只返回原结果，不能重放处置。申请 run 成功只表示建单成功。
- 本块没有接入模型工具、前端交互、会话等待检查点或自动续接。SQLite 功能验证不代表 MySQL 并发锁验证；后者单列。
- 验证与限制见 [AP-02B 持久申请](./Agent层验证记录/AP-02B持久申请.md)。

## 职责建议

1. 判断哪个动作需要谁来审批，不能由模型文字授予权限。
2. 整理待审批动作、目标、参数、原因及预期影响，经后端创建或关联工单。
3. 将等待审批的信息与逻辑会话、运行、计划步骤关联，持久化后结束当前请求，不占用 SSE 等待人工。
4. 接收可信通知或查询后端确认结果，处理拒绝、过期、撤销与重复回调。
5. 根据后端真实结果终止或续接任务；治理接口已执行的动作不由 Agent 重复执行。

## 关键衔接事项（待设计确认）

- 后端工单状态是审批/处置真值源，不另建互相矛盾的审批状态机；运行等待状态属于执行生命周期，需与既有运行状态契约对齐。
- 人工等待可能超过当前整次运行 180 秒预算。挂起、工作执行时间、人工等待期限与续接预算需要明确；不得用无限 HTTP 等待或反复新建运行重置预算绕过限制。
- 工单绑定动作、目标和参数版本；重要参数修改不得复用旧批准。何时允许管理员直接修改处置、何时需新申请，需要匹配现有后端规则。
- 管理员批准治理动作与当前用户确认偏好是不同权限；审批者身份由后端验证，不能仅信任前端事件或模型输出。
- 重复批准、重复通知与恢复不得重复处置；续接核对源工单、逻辑会话、权限及目标状态。
- LangGraph 等恢复可能重入节点；审批前的副作用需幂等，不能假定所有框架都从中断指令的下一行原地继续。
- 后端管理端 resolve 已执行治理动作；本层读到 executed 应记录结果并续接后续步骤，不能再次调用 hide/delete/ban。
- 既有系统巡检可只创建工单并结束本轮，不强制为每个工单挂起一个用户会话；只有依赖人工结果的后续任务需要续接。
- 第一批覆盖治理动作还是同时涵盖 Wiki 发布等审批，尚待用户选择。

## 2026-10-28 用户确认的审批原则

### A-D01：提交挂起，批准恢复，不占连接（已确认）

- 用户要求待审核清单提交后停下相关工具，人工等待不占连接。
- 用户确认术语：“提交时挂起，批准后恢复；已由后端执行的动作不重复执行”。
- 受审批约束的动作及其依赖步骤在待审批期间不得执行；运行应保存可续接信息并释放当前请求，不用未结束的 Promise/SSE 代替持久等待。
- 批准后确认后端结果；已 executed 的动作只读取执行结果并续接后续步骤，不能再执行同一动作。若只是批准未执行，则仍须通过后端校验后首次执行。
- 拒绝、过期、取消的具体处理及恢复预算尚需设计；不从本条推断自动批准、自动重试或权限提升。

### A-D02：后台巡检与前台聊天独立（已确认）

- 用户要求“巡检线程在后台巡线，前台继续聊天”。
- 后台巡检独立运行；某个巡检项进入审批不冻结前台用户会话，也不将系统工单错误归属给当前聊天用户。
- “线程”沿用此前已确认的逻辑执行单元含义，不因此创建操作系统子进程/工作线程。
- 一项任务的等待不应阻塞无依赖任务；同一目标在其他后台任务中的重复操作需由后端状态与幂等规则约束。

### A-D03：身份与权限通过后端强制校验（已确认）

- 用户原话：“权限和后端的双校验身份认证绑定……不能提示词来软约束权限，而是根据后端写死的身份校验。只有管理员可以改后端身份”。
- 服务凭证与用户凭证的双重身份校验沿用现有用户请求链路；认证后仍需校验角色、动作、目标和数据范围，双凭证不自动授予处置权限。
- 后端身份与确定性权限规则为授权真值源，前端自报身份、模型输出、提示词、个人记忆均不得改变身份或提升权限；Agent 工具策略是额外检查，不替代后端复核。
- “后端写死”按不可由模型改写的代码规则理解，不将用户账号身份硬编码；执行/恢复时读取有效身份和权限，不仅信任旧会话快照。
- 用户明确身份变更由管理员控制；具体受保护身份字段范围尚待澄清。当前代码允许教师审核助教认证（identity/router.py 的 assistant-certification/review），是否也收归管理员需要用户拍板，不能静默移除原教师审核权限。
- 后台巡检沿用服务级身份、受控接口与专用能力，不冒用某位管理员或复用前台用户令牌。

## 当前最小流程快照

后端身份/权限校验 → 形成明确动作与待审核清单 → 后端持久化工单及关联 → 挂起相关执行并释放请求 → 后台与其他会话继续工作 → 管理员审核 → 后端再次校验并执行/拒绝 → Agent 核对真实结果 → 幂等续接后续步骤或终止。

此快照概括用户已选原则与衔接建议，不表示新增会话等待状态、检查点或恢复接口已实现。

### A-D04：教师审核助教资格的例外保留（已确认）

- 用户选择：“保留教师审核助教资格；管理员控制账号角色等其他受保护身份字段”。
- 本条细化 A-D03：不取消现有教师助教资格审核能力；账号角色等其他受保护身份字段由管理员控制，普通用户和模型不能自行修改。
- 助教能力仍依赖后端当前身份与认证状态，不能由提示词或客户端字段激活；审批、执行及会话恢复需重新检查相关权限。
- 本条不修改现有代码，也不自动扩展教师可修改的身份字段。

### A-D05：治理先查现状、告知管理员、确认后复用后端 API（已确认）

- 用户原话：“agent进行治理先核对后端状态，先告诉管理员现状，然后确认后直接复用后端api进行治理”。
- Agent 提出治理动作前，查询后端当前目标状态，以后端返回为准，不用记忆、旧模型输出或前端快照代替现状。
- 向管理员展示目标、当前状态、建议动作与理由/预期影响，明确哪些是后端事实、哪些是 Agent 建议，等待管理员明确确认。
- 确认前不执行治理动作；确认后通过现有后端治理 API 执行，不新增绕过后端的 Agent 直接删帖、隐藏或封号实现。
- 与既有 resolve 接口衔接：管理员确认若已调用后端 resolve 并完成处置，Agent 仅核对结果；不能在收到确认通知后再重复调用同一处置。
- 助手一致性建议：后端执行时再次检查调用身份、权限和目标状态。若确认后目标或动作的关键条件变化，停止旧动作并更新现状重新确认；不得把批准旧状态理解为批准任意新状态。
- 治理 API 的适配层应复用授权能力：现有管理端接口需要真实管理员身份，服务令牌或模型声称“管理员已同意”不能代替。具体由管理员前端提交 resolve，还是由 Agent 使用受控授权调用，在后续接口设计中确定。
- 本条确认治理用例的交互与执行方向，不自动把已确认的整个人工等待恢复机制视为实现完成。

## 治理流程当前有效快照

查询后端当前状态 → 向管理员展示事实与拟治理动作 → 保存待审信息、挂起相关动作并释放请求 → 管理员确认 → 后端重新核对权限及目标状态 → 复用既有治理 API 执行一次 → Agent 核对真实结果并反馈/续接。

若管理员拒绝则不执行；若目标已变化，按待确认的失效与重新确认规则处理。后台巡检与无依赖的前台聊天继续运行。

## 2026-10-28 对外管理员凭证与准备实施

### A-D06：外部 Agent 经密钥接入管理员能力（已确认方向）

- 用户原话：“外部接入需要密钥凭证，进来就是管理员，然后你可以准备开始写了，不懂的直接问我”。
- 有效外部专属密钥对应预先配置的管理员能力；无凭证、错误凭证拒绝，不能通过请求自报 role 获得权限。
- 本条取代“所有外部客户端默认仅 read”的目标范围，既有只读实现不因讨论而自动升级。
- 管理员身份仍须落到后端可验证的身份/授权映射，不能只在 Agent 中构造 role=admin。密钥撤销、关联身份降权或封禁应使新调用与续接校验失败。
- 此次未取消已确认的高风险人工审核边界，外部 Agent 持管理员能力密钥也不能由模型自行伪造人工批准。
- 现有 MCP token→name/scopes 配置尚无后端管理员身份映射；管理员查询工具、审批操作与密钥生命周期需分批实现并记录审计。
- 用户授权准备实施，不将所有新设计需求混成一次大提交。首批建议 AP-01 后端只读现状接口，随后再接 Agent approvals 协调；不擅自更换现有框架。

### A-D05：治理复用后端 API（用户已确认）

- 用户原话：“agent进行治理直接复用后端api”。
- 治理能力和状态机复用已有后端 API；Agent 不复制隐藏、删除、封禁、警告、通知、申诉等业务执行逻辑，不直接操作数据库。
- 与既有架构衔接：Agent 经 internal-client 调用 FastAPI 白名单接口；管理员前端仍通过管理端 API 审核处置。优先复用后端治理 service 与既有工单能力，缺少的挂起/状态查询/续接关联契约后续按需要补充，不因“复用”声称现有 API 已覆盖全部审批协调。
- approvals/ 的职责聚焦于申请整理、工单关联、相关执行挂起、状态读取和幂等续接；不能把模型建议或 Agent 服务凭证当成人工批准。
- 若管理员调用既有 resolve API 已完成处置，Agent 只读取结果并续接，不再次调用处置 API；若后续支持批准与执行分离，执行 API 也必须由后端核验对应有效批准及当前权限。
- 复用 API 不等于给 Agent 配置管理员身份或将管理员令牌放入会话、提示词；此前双凭证、后台服务身份及角色限制保持。
- 本轮为设计确认，未修改生产代码或实际调用治理 API。
