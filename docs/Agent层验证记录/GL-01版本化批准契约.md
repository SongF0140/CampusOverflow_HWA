## 实现与接口

- `POST /internal/agent/user/governance-requests/v2`：服务凭证＋当前管理员JWT或后端映射外部密钥；冻结目标、动作、期限、理由和目标版本，生成规范化哈希。源身份由认证上下文派生，不接受自报操作者或来源字段。
- `GET /api/governance/approval-requests/{request_id}`：当前有效管理员读取治理审批清单，不含外部密钥指纹、JWT或未来执行租约。
- `POST .../{request_id}/approve`：人类管理员JWT，提交所看到的args_hash与说明；批准记录与唯一待执行任务同事务，返回approved及execution_id，executed=false。
- `POST .../{request_id}/reject`：拒绝并关闭关联工单，不改目标内容或账号；重复相同决定返回原终态，不能将拒绝改为批准。
- 默认 `BACKEND_GOVERNANCE_EXECUTOR_ENABLED=false`，关闭时v2创建503，旧v1不受影响。GL-02/04尚未实现，当前没有任务领取、lease签发或实际执行接口；即使显式启用本批也只会入队，不执行。
- 新表：governance_approval_requests、governance_execution_jobs。申请/工单关联与执行任务request_id有唯一约束；任务预留租约字段但本批不产生凭证。
- 7天期限在批准时复核；过期记录转expired并关闭关联pending工单，避免长期占据巡检待审队列。管理员更改目标、损坏快照或来源撤销时不能批准入队。
- 所有旧工单决策共用v2阻断，覆盖公开resolve及内部skip/处置通道；旧v1保留原行为。

## 决策说明与限制

1. v2使用独立批准记录，不复用旧manager_directed来假称“已批准未执行”，避免旧前端误显示成功。
2. 人类批准与外部管理员身份分开：有效外部密钥能提交申请，但不能调用人类批准接口。映射配置统一由纯domain函数校验，损坏/重复配置在认证和批准阶段都失败关闭。
3. 审批人取后端当前身份，重复批准不覆盖最初批准者。服务凭证、请求哈希、未来lease都不代替人类批准。
4. 请求来源指纹仅后端存储并用于撤销检查，不是私人会话文件命名空间；GL-07另行实现中台客户端稳定目录，不在此顺便迁移个人记忆。
5. 只在本地提交，不推送、不合并main，不对真实库执行迁移，不运行模型或真实治理。
