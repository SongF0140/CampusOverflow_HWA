## 集成测试设计与决策

新增 `agent/tests/integration-run.test.ts`（10 项）。与既有测试的本质差异：不再向 `createApp` 注入 mock 客户端，而是让生产装配走真实 `defaultInternalClient`（读 `BACKEND_BASE_URL`/`AGENT_SERVICE_TOKEN` 环境变量），经真实 Node fetch 与 HTTP 往返访问测试内启动的本地 mock 后端（`node:http`，随机端口）。整条链路中仅两处替身：外部 LLM（MockLanguageModelV4，SaaS 本就必须替换）与后端进程（按 `/internal/agent/*` 白名单契约响应的本地服务器）。因此请求序列、双凭证 header、user 路径前缀、蛇形字段、trace 透传、信封格式与 JSON 序列化都在真实 HTTP 层验证，而非 mock 方法调用。

BFF → Agent 一段不在本文件重复验证：BFF 转发契约（co_token 提取、header 构造、SSE 透传、503 降级）由 `frontend/src/app/api/agent/[...path]/route.test.ts` 保证，集成测试按 BFF 实际发出的请求格式（`authorization: Bearer <JWT>` + `x-trace-id`）发起调用衔接两段契约。

mock 后端对每次请求记录 method/path/query/headers/body，可按场景覆写状态码（principal、questions/search、createRun、events、finish），并真实执行后端的契约义务：RunAck/EventAck 回显 agent_run_id/trace_id/事件字段、递增 sequence_no、createRun 校验归属。这使 PersistentRunAudit 的响应关联校验（run/trace 一致、事件序号连续、终态回显）在真实 JSON 往返中生效，而不是只测 Agent 单侧。

## 覆盖内容

成功链路四条（doc_draft / suggest_tags / moderation_scan / chat）：

- doc_draft 断言完整后端请求序列（principal → runs → plan 事件 → step_started → questions/search → step_succeeded → finish PATCH），每次调用同时携带 X-Service-Token 与用户 Bearer 且 trace id 全程一致；检索走 `/internal/agent/user/questions/search` user 路径并保留 `course_id=2` 约束；审计事件体为蛇形且不含 objective；run 创建摘要为静态"用户任务：doc_draft"；终态 `{status:"succeeded", output_summary}`；响应不含用户 JWT 与服务 token。
- suggest_tags 验证词表 user 路径与真实标签 ID（tagId=5）程序映射；moderation_scan 验证正文经双凭证 user 路径读取、真实原文（而非请求方摘录）进入最终评估提示、响应只含脱敏结论。
- chat 验证零步计划也记录 plan 事件（steps 为空）、流式候选经审查后才投递 meta/delta/done、审计 succeeded、审查器与计划两次结构化调用加一次流式调用。

错误分支五条：principal 401/403 时只发生一次后端请求、不创建运行、模型零调用；工具调用中撤权 403 时事件序列为 plan → step_started → step_failed、终态 failed 且带 error_summary、不再生成最终结果、后端错误原文不泄漏；审计创建失败 503 时不进入模型与工具；审计事件写入失败 503 时停止后续工具执行并补写 failed 终态；终态写入失败 503 时已真实发生的检索与总结不得向调用方报成功。

## 真实交付状态与单列限制
