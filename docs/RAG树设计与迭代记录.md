## 2026-10-28 首轮 RAG 方案

### D-002：余弦向量召回

- 用户选择：采用余弦相似度进行语义匹配；用户理由为内容以文字回答为主，认为 DeepSeek 基模能力强。
- 技术评估：记录上述理由为用户判断，不当成验证结论。余弦是向量比较指标，embedding 模型决定表示质量，生成模型能力不能代替召回评估；具体 embedding 与分类规则未定。

### D-003：知识卡片与渐进读取

- 用户方案：借鉴 skill 渐进式披露，卡片包括领域名称、元数据（年份、tag 等）、摘要三个板块。
- 查询先检索卡片摘要，缩小范围后读取文字块，结合 query 与近期信息放入上下文。
- 用户要求元数据先筛选：根据句子中权重高的词汇匹配 tag；近期信息权重大，在 tag 层排除过时 tag。
- 尚待细化：正文切分边界、卡片与正文映射、多标签语义、过时判定、时间权重、近期信息指会话还是知识内容，以及摘要漏信息时如何补救。

### D-004：关键词与余弦向量并行召回（有效决策）

- 用户最初表述“不用关键词检索”，同条消息第 4 步提出关键词与相似度查询并行。
- 澄清后用户明确选择：“以第 4 步为准：关键词与余弦向量召回并行，再融合重排”。
- 后续设计采用此口径，替代同条消息开头的纯相似度表述。
- 用户方案：去重知识卡片后，小范围使用 Cross-Encoder 对 query/chunk 联合评估并重排，再通过 tree_summarize 合并生成答案。
- 尚待细化：召回数、融合方法、重排模型、阈值、正文读取预算、摘要合并触发条件与来源保留。

### P-001：LLM Wiki 与 Chroma 选型评估（未定案）

- 用户偏好：主观倾向 LLM Wiki，但要求与 Chroma 对比评估。
- 名称暂按 Karpathy 的 LLM Wiki 模式理解；同名具体软件尚未确认。
- 调研定位：LLM Wiki 是源资料、模型维护的关联 Wiki 与维护规则组成的知识组织模式；Chroma 是可保存 embedding、文档和元数据并进行相似度检索的基础设施，支持 cosine 与元数据筛选。
- 助手建议，未获用户确认：用卡片/Wiki 表达可读知识，用 Chroma 建可重建的摘要与正文向量索引，来源与发布状态继续由后端控制。
- 对比方案：A 原文/卡片 + Chroma；B LLM Wiki + 页面导航/搜索；C LLM Wiki/卡片 + Chroma。固定原始资料、问题集与生成模型，记录不同入库成本；不把方案差异混称为数据库性能差异。
- 拟评估：候选召回 Recall@K、重排 nDCG@K、正确且有来源的答案比例、过时内容与权限泄漏、P50/P95 耗时、入库/查询成本、更新删除传播，以及用户对答非所问、细节、可读性与等待时间的反馈。尚未实测，不报告赢家或性能数字。

### P-002：首轮技术审查建议（均待用户确认）

- 权限、明确失效与指定版本作为硬过滤；模型推断的 tag 保留软匹配或受控放宽路径，避免首层错分后无法召回。放宽不得越过权限或失效规则。
- 年份旧不直接等于知识失效；明确失效内容排除，仍有效的基础知识保留，对时间敏感问题再提高新近程度权重。
- 卡片不是完整切分方案；正文仍需按主题/标题/问答边界切分，并保留 card_id、chunk_id、来源和版本。
- 摘要召回可能漏掉细节，评估是否增设正文向量补召回。
- Cross-Encoder 本身就是重排器，不默认再串联一次同类 rerank；混合召回分数不能未经校准直接相加。
- tree_summarize 是候选证据的递归合并方法，不自动等于持久知识树。保留原始引用与限定条件，评估是否只对长证据/综合问题启用。

### P-003：针对教材的建议（未定案）

- 优先保留教材章节层级与可引用的原文块，用既定关键词/余弦混合召回、Cross-Encoder 精排；需要跨知识点关系时，再按有来源的概念关系有限扩展。
- 区分四件事：章节树（包含关系）、概念图（前置/依赖等关系）、摘要树（多层抽象索引）、tree_summarize（查询后的答案合并）。这些机制可以组合，不能互相代称。
- 图关系需要来源、关系类型与方向，抽取错误不能作为已验证教材事实；检索关系节点后仍应回到教材正文作为回答证据。
- HyDE 是先生成假想文档，再用其向量检索真实资料；假想文档不是证据。对教材精确术语、定义、版本条件，可能引入偏题与额外延迟，建议首轮不用作默认路径；若短而模糊问题的召回实测不足，再做独立对照实验。
- 当前设计属于元数据过滤、卡片摘要到正文的分层读取、混合召回与重排组合；尚未定义概念图遍历，也未定义类似 RAPTOR 的递归聚类/摘要索引构建。加入 tree_summarize 本身不等于已实现这两类索引。

### P-004：流程整理建议（待确认）

1. 理解原问题，判断是否存在影响检索的歧义；“子询问”是否向用户发出，已单独提问等待回答。
2. 拆分子问题，为同一子问题生成不同检索表达；查询聚类保留子问题边界，不将不同的信息需求压成同一问题。
3. 按权限、有效版本等元数据约束检索；每个子问题执行关键词/余弦混合召回，再融合、去重与有限概念关系扩展，按卡片定位原文块。
4. 初筛候选前 5 个，Cross-Encoder 联合评估 query 与正文块后取前 3 个。rerank 是操作，Cross-Encoder 是其实现方式，不默认重复执行两轮。
5. 候选最终确定后再围绕子问题归纳证据；每个子问题的 tree_summarize 输出带原文来源、限定条件与未解问题，再按原问题合并。多查询融合不等于多次总结，避免对每个同义查询重复生成答案。
6. 多子问题时“5→3”是每个子问题还是整次运行全局，尚未确认。助手建议优先评估每个子问题 5→3，并加整次运行证据/token 预算；全局仅 3 块可能漏掉部分子问题。
7. 初筛分数暂称融合相关性分数，不能直接混加 BM25、余弦与精排原始分数，也不能当成正确率；保持最低证据门槛，不足 3 条时不强凑。
8. HNSW 暂停按用户决定执行；性能结论待测。小规模可评估 Flat 精确检索基线，但它不保证比 HNSW 更快，不自动替用户选定。
