## M-D01：账号隔离与渐进式上下文（用户已确认）

- 用户原话：“每个人单独账号访问的时候会把记忆+到他访问的上下文中，而这里上下文是渐进式披露的”。
- 用户访问时，读取当前账号自己的个人记忆，加入其访问场景的上下文。
- 上下文采用渐进式披露，不把所有个人记忆一次性加载给模型。
- 继续遵守浏览器按账号隔离与清空要求；用户未改变当前记忆存储位置，也未要求个人记忆改存公共 Markdown 知识库。
- 用户未在本条授权自动新增、更新或删除个人记忆；产生与维护方式仍需沿用已确认边界或另行设计。

## M-D02：三层渐进披露方案（用户已确认）

用户于 2026-10-28 回复“是这样的设计”，确认前一轮提出的三层披露方案：第一层相关偏好/主题/索引，第二层按课程、问题或任务展开摘要，第三层在需要时读取具体条目。披露指模型实际收到的内容逐步增加，而非界面折叠。

| 层 | 披露内容 | 目的 |
| --- | --- | --- |
| 第一层 | 与当前场景相关的简短偏好、记忆主题或条目索引 | 用较少上下文判断哪些记忆值得展开 |
| 第二层 | 与当前课程、问题或任务相关的记忆摘要 | 为当前回答选择必要背景 |
| 第三层 | 仅对仍需细节的条目展开具体内容 | 补足证据或偏好细节，避免全量读取 |

以下为衔接与实现注意事项，不能将本轮对三层方案的确认扩大为具体协议、自动记忆写入或所有工程细节已定案：

- 披露的“层”指模型收到的内容，不只是页面折叠；不能先把完整记忆发给模型，再声称只披露摘要。
- 访问账号及其权限来自可信登录链路，不能根据记忆文本指定账号。浏览器命名空间隔离是产品行为，不应宣称抵御同源脚本或恶意篡改的安全隔离。
- 建议建立上下文装配职责，将账号记忆、当前会话和有权查看的教材/认证问答来源分别标识；个人记忆不是站内知识证据，也不能授予访问或工具权限。
- 若需多轮按需读取浏览器条目，应明确前端与 Agent 的披露协议；当前单次发送最新 20 条的接口不自动具备按需回取能力。
- 清空后后续请求不再注入；账号切换应同时丢弃上一账号在客户端及服务端会话中的已装配缓存。已发送上下文的在途运行如何取消或失效，需要单独明确，不能声称浏览器删除能撤回已发数据。

### M-D04：用户“线程”为隔离的逻辑会话（用户已确认）

- 用户原先以“主agent的子进程里面新建一个线程”描述用户访问方式。
- 经澄清后选择：“独立会话执行上下文：隔离账号、历史、记忆和运行状态，共享 Agent 服务（推荐）”。
- 当前有效目标为共享 Agent 服务内的逻辑会话隔离，不要求为每个用户创建操作系统子进程或 worker thread。
- 每个会话独立装配账号、历史、渐进式个人记忆与运行状态；单次运行 ID 不能自动代替持久会话 ID。
- 当前生产代码有请求级 principal/internalClient/runControl 及运行 ID，但未发现主 Agent＋持久用户会话管理模块，也未发现 child_process/worker_threads 用户执行实现。不能将已有请求隔离描述为完整会话架构已落地。
