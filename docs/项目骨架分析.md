# CampusOverflow AI 项目骨架分析

> 状态：草案，可继续微调  
> 目标：为后续创建代码仓库、分工和任务拆解提供目录依据。

## 1. 骨架设计原则

项目包含前端、业务后端、Agent 服务和部署配置。目录应让团队成员一眼看清每个服务的职责边界。

原则：

- 前端、后端、Agent 服务物理分离。
- 核心业务代码按领域模块组织。
- Agent 工具、循环、提示词和日志独立组织。
- 文档、部署、脚本和测试放在固定位置。
- 不把 AI 能力散落在普通 CRUD 模块里。

## 2. 推荐顶层目录

工作区根目录存放文档、规格与工程规则；代码服务统一放在 `campus-overflow-ai/` 总目录下。


### 3.2 前端状态建议

第一阶段可以不引入复杂状态库。

建议：

- 登录用户信息：Context 或轻量状态库。
- 服务端数据：封装 fetch hooks。
- 表单状态：组件内部状态。
- Agent 流式结果：独立 hook 管理。

如果后续复杂度上升，再考虑 TanStack Query。

## 6. Agent Loop 文件职责

| 文件 | 职责 |
| ---- | ---- |
| agent-loop.ts | 串起感知、规划、工具调用、自检和记录 |
| task-classifier.ts | 判断任务类型，例如标签推荐、审核扫描 |
| risk-policy.ts | 判断风险等级和允许动作 |
| self-check.ts | 校验模型输出是否符合结构、来源和安全要求 |
| registry.ts | 注册允许调用的工具 |
| backend-client.ts | 封装和 FastAPI 的服务间调用 |

关键点：

- loop 是运行模型，不是一次性函数集合。
- task 是 loop 可处理的任务类型，不是固定 workflow 节点。
- tools 是 Agent 可以选择的动作集合。
- risk-policy 决定 Agent 能不能执行某个动作。

## 11. 第一阶段最小骨架

第一阶段不需要一次性建满所有目录。推荐最小骨架：

```text
campus-overflow-ai/
├── frontend/
├── backend/
├── agent/
├── deploy/
└── docker-compose.yml
```

每个服务只先保留能启动、能健康检查、能互相调用的最小代码。

第一阶段验收：

- 前端能打开首页。
- 后端能返回 /health。
- Agent 能返回 /health。
- 前端能调用后端接口。
- 前端能调用 Agent 接口。
- Agent 能调用 FastAPI 内部测试工具。
- Docker Compose 能启动所有基础服务。

## 12. 后续微调点

- 是否使用 monorepo 包管理工具。
- 前端是否引入 TanStack Query。
- 后端是否使用 async SQLAlchemy。
- Agent 服务使用 Express、Hono 还是原生 Node server。
- Agent 是否需要独立任务队列。
- Redis 是否第一阶段就进入 docker-compose。
- 管理后台是独立 React 页面还是复用主前端布局。
