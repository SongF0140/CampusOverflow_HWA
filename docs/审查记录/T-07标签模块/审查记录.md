## 决策说明

1. **标签归属 qa 模块而非新建模块**：架构说明第 3 节将"标签"明确划入 qa 职责（`/api/tags` 前缀已定案），与 T-06 评论同理由。Tag 与 QuestionTag 模型放 `qa/models.py`，仅被本模块 repository import（lint-imports 强制）。
2. **绑定请求体定案为 `[int | str]` 二态**：接口设计指南 §3.7 草案 `{ tagIds: string[] }` 有歧义——前端选择已有标签拿到的是数字 id，新建自定义标签只有名字。定案：int=已有标签 id（不存在→400 TagNotFoundError），str=新自定义标签名（归一化后内联创建 type=custom；同名标签全局唯一并复用已有行，避免同名分裂）。发布入参 `tag_ids: list[int]` 保持纯 id（发布时没有"选完又改名"的歧义，自定义标签经绑定接口或由 str 混入发布 tag_ids 也可行——定案发布同样接受二态，统一走 `_resolve_tag_refs`）。接口文档 §3 已按蛇形回填。
3. **绑定语义=增量追加**：POST 绑定接口为"追加绑定这批标签"而非"整体替换"。理由：E-03"重复绑定被拒绝"只有在此语义下才成立——替换语义下重复传入是幂等正常操作，不存在"拒绝"可测。追加语义同时简化前端（勾选即追加）。上限校验按"当前已绑 + 新增"计算（`ensure_tag_count_within_limit`），与发布的 0+n 对齐，QUESTION_MAX_TAGS=5 统一约束两个写入点。
4. **每问题标签上限 5（QUESTION_MAX_TAGS=5）**：需求文档未定具体数值，主流问答平台（Stack Overflow 5 个）取 5。**审查可调**——改 domain 常量即可，表结构无影响。
5. **标签 id 不存在归 400 而非 404**：绑定接口的 URL 定位资源是问题（不存在→404），tag_ids 是请求体参数的一部分——参数指向不存在的实体属参数错误（400），与"父评论不存在→400"（T-06）同一口径。
6. **E-09 写入点收口**：全模块仅发布（发布入参 tag_ids）与绑定（POST /api/questions/{id}/tags）两处写 tags/question_tags。AI 推荐标签（E-09"未经确认不写入"）本期仅预留：第二阶段 Agent 推荐结果须先回显给用户，用户确认后调用绑定接口——绑定接口即确认动作本身。测试以 `assert db_session.query(Tag).count() == 0` 锁定"不调接口零写入"行为。
7. **E-03 双层防御**：应用层 `ensure_not_already_bound`（请求内重复 + 与已绑交集，400）先行；库层 `uq_question_tags_pair` 唯一约束兜底并发窗口。tags 表唯一性由 `ix_tags_name` 唯一索引承担、不另建 UniqueConstraint——MySQL 下唯一约束自动建同义索引，alembic check 会报冗余（板块1 实测踩坑）。
8. **hot 模式语义**：按可见问题绑定数降序取前 10（HOT_TAGS_LIMIT=10），having count>0 排除零绑定标签（热门=有人用）；question_count 统计经双重 outerjoin 只计未软删问题（E-10 口径），非 hot 模式 question_count 同口径回填。排序 `Tag.id asc` 兜底稳定序。
9. **发布失败原子性**：发布入参带 tag_ids 时，问题创建与标签解析/绑定在同一事务；绑定失败（400）则问题行随会话回滚，不产生无标签孤儿问题。repository 全程 flush 不 commit（D-8）。
10. **列表/详情 tags 回填防 N+1**：沿用 T-05 批量模式——`get_tags_by_question_ids` 一次取回当页全部问题-标签对，service 内按 question_id 分组回填；绑定排序按 `QuestionTag.created_at + Tag.id`，保证展示顺序稳定。
