## 决策说明

1. **采纳事务本期仅落问题侧（三步缺二）**：架构说明 4.B 定义"置采纳 → grant_reputation(+15) → notify"三步事务，但 ReputationLog/Notification 表属 interaction 模块（T-08/T-10），且 qa 不得写 interaction 表（D-2）。本期 commit 内只做置采纳 + resolved，service 留 `# TODO(T-08)/# TODO(T-10)` 钩子注释；接口文档 §4 注明声誉/通知随 T-08/T-10 回填。放弃方案：提前建 interaction 两表（拆散 T-08/T-10 范围）。E-05 并发竞争由 questions.accepted_answer_id 唯一约束兜底（commit 捕获 IntegrityError 转 AlreadyAcceptedError 400）。
2. **采纳数据源落 questions.accepted_answer_id 列**：与 answers 侧不设 is_accepted 冗余标记，单一事实来源；T-04 占位注释已预告本列。循环 FK（questions↔answers）用 use_alter=True 标记，Alembic 生成"先建 answers 再 ALTER questions"的迁移；修复了 SQLite 测试环境 drop_all 的 SAWarning（每测试 1 条，88 条）。
3. **回答资格：任何登录用户**：学生端接口文档 §4"谁调用？登录用户"，未设课程成员限制（与发问题的 403 资格不同），按文档实现；E-07 封禁由 get_current_user 统一拦截。
4. **已采纳回答被删 → 级联撤销采纳**：文档未定义此边界；若允许留下悬空 accepted_answer_id 会破坏 E-05 语义，若禁止删除则新增文档没有的规则。取最小意外：软删回答的同一事务内 unaccept（清空引用 + 状态回退 published），测试覆盖（test_delete_accepted_answer_unaccepts_question）。审查可改。
5. **回答正文上限复用 BODY_MAX_LEN=20000**：文档未给回答正文上限，E-02 为通用条款；复用问题正文常量保持一致，截断提示文案独立（"回答成功（正文超长已截断…）"）。
6. **certify 幂等 + 管理员不放行**：D9 定案 require_roles(teacher)，管理员也 403（测试覆盖）；POST/DELETE 重复调用幂等（重复置位无副作用），文档未写错误清单故不引入 400。
7. **sort=votes 暂与 latest 同序**：投票分依赖 T-08，repository 注释注明回填点；sort=accepted 将被采纳回答置顶（`(Answer.id == accepted_answer_id).desc()`），时间戳秒级精度下补 id 次级排序保证稳定。
8. **回答数批量统计**：T-04 占位的 answer_count/has_accepted/accepted_answer_id 本次回填；列表页一次 GROUP BY 批量统计（count_answers_by_question_ids），避免 N+1（同 T-03 用户名批量模式）。
9. **板块 3+4 合并提交**：schema 必填字段（answer_count/has_accepted/accepted_answer_id 去默认值）与 service 构造点回填互为依赖，单独提交板块 3 会使 HEAD 上接口测试红；合并为一个提交保证每次提交自洽。
