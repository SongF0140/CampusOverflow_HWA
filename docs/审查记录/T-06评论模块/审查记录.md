## 决策说明

1. **评论归属 qa 模块而非新建模块**：架构说明第 3 节将"评论"明确划入 qa 职责（Comment 模型与 `/api/comments` 前缀已定案），interaction 只承载"内容的衍生写"（投票/声誉/通知）。故 T-06 是 qa 模块扩展，不新建 interaction——与 tasks.md 里"评论触发通知"不冲突：通知本体属 interaction（T-10），评论侧仅留 `# TODO(T-10)` 钩子。
2. **挂载目标用"二选一列 + CHECK 约束"而非父表多态**：`question_id`/`answer_id` 双可空列 + `ck_comments_target_exclusive` CHECK（恰一非空）。替代方案是单 `target_type`+`target_id` 多态列，但会丢失数据库级 FK 完整性；CHECK 在 MySQL ≥8.0.16 与 SQLite（测试）均为可检查约束。
3. **二级规则收窄为"父评论必须同目标且为顶级"**：spec US-05 只说"支持二级回复"，未定回复的回复是否合法。定案：`ensure_parent_in_same_target`（跨目标回复 400）+ `ensure_top_level_parent`（回复的回复 400）——防止任意深度嵌套，前端渲染只需两层，数据层也不需要递归。接口文档 §5 已回填此定案。
4. **列表"分页只作用顶级评论、回复全量嵌套"**：接口文档 §5 原文（camelCase 时代）含糊。定案：`total` 与 `page` 只针对顶级评论；二级回复按 `parent_id` 全量归组进 `replies`，不重复作为顶级条目。理由：评论流以顶评为分页单元是社区产品惯例，回复数量少（二级限制下天然有界）。作者名一次批量取（顶评+回复去重合并），沿用 T-05 的防 N+1 模式。
5. **评论上限 1000 字（E-02 截断提示）**：接口文档未定评论长度。问题/回答正文 20000 字对评论明显过宽，取 1000 字（短文本定位，主流平台评论上限量级）；常量 `COMMENT_MAX_LEN` 独立定义不与 BODY_MAX_LEN 耦合，清洗复用同一 `_CLEANER`（X-03 规则单点）。**审查可调**——若用户认为应更宽（如 2000），改常量+迁移列宽不受影响（Text 列）。
6. **删除顶级评论级联软删其直接回复**：接口文档只说"软删除"，未定父子联动。参考 T-05"已采纳回答被删级联撤销采纳"的一致性思路：父评论软删后回复若保留会孤儿化（回复只能挂在已不可见的父评论下）。二级限制下层深恰好一层，级联成本 O(1) 条 UPDATE，与父删除同一事务。替代方案（回复提升为顶级）会篡改作者语义，放弃。
7. **E-07 补评论专项测试**：封禁拦截统一在 `get_current_user`（T-04 时已钉住发帖路径），评论本可豁免；但覆盖检查器以"规则编号被测试引用"为判据，且评论是 US-05 独立接口面，补 1 项 `test_banned_user_cannot_comment_403` 成本极低、显式钉住评论路径。
8. **评论排序为创建时间正序**（`created_at asc, id asc`）：问题/回答列表按最新优先（信息流语义），评论流按对话时序正序（阅读语义）；id 作次级排序规避秒级时间戳同序不稳定问题（沿用 T-05 惯例）。
